# Security policy and threat model

Wallet secrets stay in a local JSON file, excluded from Git by default. `.env`, `.data`, build products and development caches are ignored. The local wallet uses Ed25519 generated by the official Sui SDK. Creation uses an exclusive file open, restrictive directory/file permissions (700/600), and refuses corrupt, mismatched, insecure or symlink wallet files. Existing wallets are never silently replaced.

The wallet file is **plaintext at rest**. This is process-boundary isolation, not a hardware wallet or protection against a compromised OS, same-user malware, debugging, heap dumps, terminal recording or malicious dependencies. Use a dedicated OS account, encrypted disk, restrictive backups and Testnet funds. JavaScript does not guarantee erasure of secret strings. Do not store this repository's data in a shared directory.

## Boundaries

- Only an explicit local terminal callback displays the private key. This callback is not a tool result, model message, remote logger or memory write. Export is not an LLM-callable tool.
- Tool outputs expose public wallet metadata only. The OpenRouter message boundary rejects known credentials and likely secret patterns before sending. Provider authentication uses the OpenRouter key in its HTTP authorization header, never prompt content.
- User input is screened before provider calls. The guard recognizes registered application credentials, Sui key encodings, common credential syntax, raw key patterns, JWTs and valid English BIP39 mnemonic windows. Detection is heuristic, with possible false positives and false negatives; it is not universal data-loss prevention. Never paste any secret into chat, even in encoded or split form.
- Secret values are registered for redaction. SDK errors are not logged or returned verbatim. No remote logging or telemetry is implemented. Do not enable external HTTP debug logging or send process dumps to services.
- Memory writes need explicit local user intent and the exact authorized text. Model-generated or recalled instructions cannot authorize a write. Memory content is not appended to model context. Likely secrets retrieved from older memory are blocked from display.
- Default MemWal sends plaintext to its relayer; the relayer embeds, Seal-encrypts and uploads. The delegate key authenticates signed requests. It is a secret and must never be stored as memory or used as the owner wallet key.
- Verified tool sections are deterministic. Generated prose is never displayed. “Verified” means obtained from the named tool/client, **not** independently proven or Nautilus-attested. A configured RPC/relayer remains a trust boundary. Custom endpoints must actually serve the configured network.
- Terminal control characters in result values are JSON-escaped. Blockchain amounts use integer arithmetic. No generated value is accepted as transaction state.

## Operational rules

Testnet is the default. Mainnet requires explicit configuration and a separate wallet file. No transaction tool exists, so no automatic Mainnet spending is possible. A stored maximum-spending preference is not enforced on-chain.

Custom `WALLET_FILE` paths must be in a private directory and explicitly excluded from Git. Windows filesystem permission semantics differ; use restrictive ACLs. Back up keys offline. Revoke compromised MemWal delegates through account-owner controls, rotate provider keys, and replace any compromised wallet.

Gitleaks scans repository content in CI. It is also available locally as `gitleaks dir . --redact`. Review staged files and secret-scan before publishing. Never include `.env` or `.data` in bug reports. A private key cannot be made safe again by deleting its Git history.

Report vulnerabilities privately to the repository maintainer using GitHub private vulnerability reporting when enabled. Include reproduction steps with synthetic credentials only. Maintainers should enable private reporting and branch protection before accepting outside contributions.
